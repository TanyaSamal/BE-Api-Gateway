# Интеграционный тест: Analytics Service Down - Queue Persistence

## 📋 Описание

Интеграционный тест эмулирует падение микросервиса аналитики и проверяет:
1. **Сохранение событий в очереди RabbitMQ** - события остаются в очереди при недоступности микросервиса
2. **Распространение x-correlation-id** - идентификатор корреляции передается во всех логах и сообщениях
3. **Устойчивость к сбоям** - система продолжает работать без потери данных

## 🎯 Сценарии тестирования

### Сценарий 1: Отправка события и валидация x-correlation-id
- Отправляет POST запрос `/analytics/track` с событием
- Проверяет наличие `x-correlation-id` в заголовках ответа
- Валидирует успешный статус ответа (201)
- Проверяет, что `x-correlation-id` залогирован во всех логах

### Сценарий 2: Проверка сохранения сообщения в очереди RabbitMQ
- Отправляет несколько событий при недоступности микросервиса
- Проверяет, что события остаются в очереди (не удаляются)
- Валидирует структуру сообщения в очереди
- Проверяет наличие `x-correlation-id` в заголовках сообщения RabbitMQ

### Сценарий 3: x-correlation-id во всех логах
- Отправляет событие на трекинг
- Захватывает все логи во время обработки
- Валидирует, что `x-correlation-id` присутствует во всех логах

### Сценарий 4: Повторная попытка отправки при восстановлении
- Отправляет событие в очередь
- Проверяет, что событие остается в очереди
- Валидирует сохранение `x-correlation-id` для возможной переобработки

### Сценарий 5: Валидация формата x-correlation-id
- Проверяет, что `x-correlation-id` соответствует формату UUID v4
- Валидирует, что идентификатор уникален и имеет корректную длину

## 🚀 Запуск тестов

### Предварительные требования
- RabbitMQ должен быть запущен на localhost:5672
- API Gateway должен быть готов к приему запросов
- Node.js 16+ и npm 7+

### Запуск всех интеграционных тестов
```bash
npm run test:e2e -- analytics-service-down.integration.spec.ts
```

### Запуск с дополнительным логированием
```bash
npm run test:e2e -- analytics-service-down.integration.spec.ts --verbose
```

## 🔍 Что проверяется в каждом сценарии

### Сценарий 1 - Проверяемые аспекты:
- `response.headers['x-correlation-id']` определен и не пустой
- `response.status` === 201 (успешное создание)
- `response.body.success` === true
- Логи содержат `[ID: {correlationId}]` паттерн

### Сценарий 2 - Проверяемые аспекты:
- Количество сообщений в очереди ≥ 2 (для двух отправленных событий)
- `message.content` парсируется как JSON
- `message.properties.headers['x-correlation-id']` соответствует отправленному ID

### Сценарий 3 - Проверяемые аспекты:
- Наличие логов от `AppLogger` с тегом `[Log]`
- Каждый лог содержит `[ID: {correlationId}]`
- Логи от `GatewayService` содержат идентификатор корреляции

## 🐛 Возможные проблемы и решения

### RabbitMQ не доступен
Тест автоматически пропустит проверки очереди, если RabbitMQ недоступен.

**Решение**: Запустите RabbitMQ:
```bash
docker run -d -p 5672:5672 rabbitmq:3.12
```

## 📝 Структура файла теста

**Расположение:** `apps/api-gateway/test/analytics-service-down.integration.spec.ts`

**Размер:** 304 строк TypeScript кода

**Главные компоненты:**
- `beforeAll` - инициализация приложения и подключение к RabbitMQ
- `afterAll` - очистка ресурсов и закрытие подключений
- 5 describe блоков с 5 тестами каждый
- Перехват console.log/error/warn для проверки логов
- Взаимодействие с API Gateway через supertest
- Проверка RabbitMQ очереди через amqplib

## 🔐 Требования к безопасности

- ✅ `x-correlation-id` должен быть уникальным для каждого запроса
- ✅ UUID v4 обеспечивает криптографическую уникальность
- ✅ ID передается по всей цепи обработки
- ✅ Логирование содержит полную информацию для аудита
